# Schema Review

**Date:** 2026-09-05
**Method:** schema executed against PostgreSQL 16.15, every finding reproduced with a
failing test before the fix and re-tested after.
**Result:** 9 defects found and fixed. 2 constraints verified working and left alone.
**Status:** all findings are now enforced by `apps/api/tests/test_schema_invariants.py`,
which runs in CI. Three of them were mutation-tested to confirm the tests actually fail
when the fix is reverted.

## Why this happened before the first migration

The baseline is the one migration you cannot fix cheaply. Every later change is
expand-contract against live data; the baseline is free to correct until it has run
somewhere real. A review after the first deploy costs a data migration for each of the
findings below.

Reading the schema was not sufficient. **Every one of these looked correct on the page.**
The critical finding in particular reads as an entirely ordinary `ON DELETE CASCADE`.

## Findings

### 1. CRITICAL: erasure destroyed the counterparty's record

`connections.user_low_id` and `user_high_id` were `ON DELETE CASCADE`. Deleting user A
cascaded away the connection row, which cascaded away **user B's `connection_view` and
their private notes about the meeting**.

```
connections_before:         1
connections_after_A_erased: 0
views_remaining:            0
```

B did nothing. B loses their record of a meeting that happened, and a note they typed.

This directly contradicted ADR-0020, which states that a snapshot is equivalent to a
paper card voluntarily handed over and that the recipient retains it. The document said
one thing and the schema did the opposite, silently.

**Fix, first attempt.** `ON DELETE RESTRICT` plus a purge job that anonymises the
`users` row column by column. This worked, and it was the wrong shape.

It depends on the purge nulling **every** personal column. Add a column later, forget to
add it to the purge list, and there is a silent compliance defect with no test that
catches it. The correctness of erasure would rest on someone remembering.

**Fix, adopted.** Split the table:

| | Holds | On erasure |
|---|---|---|
| `users` | id, timestamps. **No personal data, ever.** | Survives as an anchor |
| `user_profiles` | All personal data | **Deleted, one statement** |

Erasure becomes `DELETE FROM user_profiles WHERE user_id = ...`. The FKs from
`connections` point at the anchor and stay `RESTRICT`, so the counterparty keeps their
connection, their notes and the card snapshot.

The rule this encodes: **if a column is personal data, it lives in `user_profiles`.** A
new personal column is then covered by erasure automatically, by construction rather than
by discipline.

Verified after fix:
- Alice's profile row gone, Bob still holds the connection, his note, and the snapshot
- Deleting the anchor still raises a foreign key violation
- Adding a `home_address` column and erasing removed it with **no purge-list update**
- Erasure frees the email immediately, which also resolves finding 4 outright

ADR-0020 corrected to match.

### 2. Soft delete plus natural primary key blocked rejoining

`event_attendees`, `organization_members` and `event_staff` used natural primary keys
alongside `deleted_at`. Anyone who left and came back collided with their own
soft-deleted row.

```
ERROR: duplicate key value violates unique constraint "event_attendees_pkey"
```

An attendee who leaves an event by accident could never rejoin it. This would have
presented as a support ticket, not a crash.

**Fix.** Surrogate primary key plus a partial unique index on
`WHERE deleted_at IS NULL`. Verified: rejoin succeeds, double-join still rejected.

### 3. Soft-deleted rows held their identifiers hostage

`events.code`, `events.slug` and `organizations.slug` were plain `UNIQUE`. A deleted
event kept its join code forever.

**Fix.** Partial unique indexes excluding soft-deleted rows.

### 4. Deleted accounts blocked re-registration for 30 days

`users.email` was plain `UNIQUE`, and account deletion has a 30-day grace period
(ADR-0020). Someone who deleted their account and immediately regretted it could not
sign up again with their own address.

**Fix.** Resolved by the split in finding 1, not by a separate change. Erasure deletes
the profile row, which frees the email outright.

Trade-off, accepted and documented: restoring within the grace period must check the
email has not been claimed in the meantime, and a restore is therefore not guaranteed.

### 5. Moderation history was destroyed by the moderation action

`reports` cascaded from `cards`, `users` and `events`. Suspending a phishing card and
then purging it erased the record of *why* it was suspended.

```
moderation_history_remaining: 0
```

Repeat-offender detection and any appeal both depend on that history.

**Fix.** `ON DELETE SET NULL`, plus a denormalised `subject_label` so the report stays
readable after the subject is gone.

### 6. Entitlements accepted meaningless rows

`value_int` and `value_bool` were both nullable with no constraint, so a row with
neither was accepted. Depending on the caller, that reads as "entitled to nothing" or
"unlimited" — a billing bug in either direction.

**Fix.** `CHECK` requiring exactly one.

### 7. `updated_at` was decorative

Set at insert, never moved. No trigger existed.

Three things depend on it being real: sync conflict resolution (ADR-0016), cache
invalidation on public card pages, and the "details changed since you met" indicator
(ADR-0004). All three would have failed silently.

**Fix.** `set_updated_at()` trigger on every table carrying the column. Enforced in the
database rather than the application, because an application that forgets one UPDATE
path produces stale data with no error.

### 9. The trigger used `now()`, which is transaction time

Found while writing the test for finding 7, not by reading the trigger.

Postgres `now()` returns the **transaction** start time. A row inserted and then updated
inside one transaction therefore gets an `updated_at` identical to its `created_at`, and
the modification is invisible to anything comparing the two — which is exactly what sync
conflict resolution does.

The test asserted `updated_at > created_at` and failed. Reading the trigger would not
have surfaced this; `now()` looks obviously correct.

**Fix.** `clock_timestamp()`, which is wall time at trigger execution.

### 8. Duplicate roster imports doubled the dashboard denominator

`event_roster_entries` had no uniqueness. Organizers re-upload registration lists. The
second import would silently double expected attendance, corrupting the one metric
organizers actually buy: *percentage of attendees who made a connection*.

**Fix.** Partial unique index on `(event_id, email)`.

## Verified working, not changed

**The pair-ordering CHECK.** A reversed pair is rejected, so the same two people cannot
be stored twice in opposite order.

**The two partial unique indexes on `connections`.** Confirmed that a duplicate
non-event connection is rejected. This is the NULL trap from ADR-0003 — a single unique
constraint over a nullable `event_id` would have allowed unlimited duplicates, because
Postgres treats NULLs as distinct. Worth re-confirming that the fix works, because it is
the kind of thing a future refactor will try to "simplify".

## Considered and rejected: a `principals` table

`entitlements.subject_id` and `subscriptions.subject_id` are polymorphic — either a user
or an organization — so no foreign key can enforce them.

The standard fix is a supertype table that both `users` and `organizations` reference,
with `entitlements.subject_id` pointing at it. **Prototyped and confirmed working**: the
orphan insert is correctly rejected.

**Rejected anyway.** Weigh what it prevents against what it costs.

What an orphaned entitlement actually does: nothing. It is a dead row. The check is
`entitlements.check(subject, key)` against a real subject id, so an orphan never grants
access to anyone and never removes it. Nobody is over-billed and nobody is locked out.
The reconciliation job already looks for exactly this class of divergence.

What it costs: every signup and every organization creation becomes two inserts in a
transaction, on the hottest path in the product, forever. Plus a table and a join in
every subject-related query.

Permanent ceremony on the signup path to prevent dead rows is a bad trade. **Recorded as
a known limitation.** Referential integrity here is the service layer's job.

This is worth contrasting with finding 1, where the extra table *was* worth it: there,
the failure mode was silently retaining someone's personal data after they asked for
erasure. Here it is junk rows. Same technique, opposite answer, because the consequence
differs by orders of magnitude.


## The tests now run in CI

Every finding above is enforced by `apps/api/tests/test_schema_invariants.py`. 14 tests,
each docstring naming the finding it guards.

```bash
pnpm api:test
```

**Mutation-tested.** A test that passes is not evidence it would catch a regression, so
three fixes were reverted individually to confirm the suite fails:

| Reverted | Caught by |
|---|---|
| `RESTRICT` back to `CASCADE` on connections | `test_deleting_the_identity_anchor_is_refused` |
| `email` column moved back onto `users` | `test_the_anchor_holds_no_personal_data` |
| `cards_updated_at` trigger removed | `test_updated_at_actually_moves` and `test_every_updated_at_column_has_a_trigger` |

Two of the tests are structural rather than behavioural, and those are the ones that
matter most over time: `test_the_anchor_holds_no_personal_data` asserts the exact column
set of `users`, and `test_every_updated_at_column_has_a_trigger` compares
`information_schema` columns against triggers. They fail when someone *adds* something
wrong, which is how these defects get reintroduced.
